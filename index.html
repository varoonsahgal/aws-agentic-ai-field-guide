Chapter 01 · Orientation

Start here

What the assessment is, the environment you'll be dropped into, the six challenges on one screen, and the one question every challenge keeps asking.

The one question

Whole guide

Which component is actually making this decision, what does it need to know, and what evidence proves it has it?

The AWS Agentic AI Demonstrated micro-credential is an exam lab, not a quiz. AWS provisions a real account with an agentic application built on Amazon Bedrock AgentCore, breaks or leaves unfinished one subsystem per challenge, and gives you about two hours to repair all six in the console. A Check button grades each challenge against its success criteria. Nothing is multiple choice, and nothing asks you to build from scratch: every challenge is "repair the deployed system, using the existing resources".

Status says READY. Evidence says working. Only evidence counts.

The environment

Same scenario in every challenge

The application is a supply-chain assistant for a fictional space-cargo company, OrbitOps. A chat console (a Lambda behind a Function URL) talks to an orchestrator agent hosted in AgentCore Runtime. The orchestrator discovers inventory, supplier, logistics and quality tools through an AgentCore Gateway, delegates document questions to a knowledge-base specialist agent, remembers operators through AgentCore Memory, and reasons with a Bedrock model wrapped in a Guardrail. Each challenge hands you this platform with one part broken: identity, tool routing, retrieval, memory, networking or content safety.

The practice labs that accompany this guide (OrbitOps: Cosmic Cargo Rescue, lab folders AM01 to AM06) deploy the same platform with the same faults, one isolated copy per student, so you can rehearse each challenge with a chat console that shows you a diagnostic trace under every reply.

Why one scenario matters

The challenges are phrased as symptoms ("every attempt ends with 'Authentication service unavailable'", "ask where a shipment went and it returns inventory counts"). Knowing the platform as one connected system turns each symptom into a location: you'll know which resource to open before you finish reading the task.

How a challenge is written

Challenge anatomy

Every challenge brief has the same four parts. The practice-lab handouts add a concept briefing, progressive hints and a debugging playbook around them.

PrerequisitesWhat is already in place and must be reused: pool ids, roles, buckets, gateway and runtime ids. Treat this list as the inventory of things not to recreate.
TasksThe repair objectives, as a checklist. Names in bold are contracts: target names, scope names, environment variable names, namespace strings.

Read this once

Model output is probabilistic. The wording of a reply will differ from any sample. The success criteria and the evidence are the contract, not the prose. "I have no quality-inspection tool connected" is data; "Here is the quality status" with no tool actually invoked is a hallucination.

Region and naming

Shared-environment etiquette

Use the Region the supplied resources live in; in the practice labs that is US West (Oregon), us-west-2, and resources are named orbit-<student id>-amNN-… (or orbit_<student id>_amNN_… for AgentCore runtimes and memories, which allow only letters, digits and underscores). In the assessment, the identifiers come from the brief's Solution resources section. Either way: choose unique names for anything you create, keep the required names exactly, and never edit a resource that isn't yours.

First thing, every time

Check the region selector before you open anything. A knowledge base created in the wrong region is invisible to a runtime in the right one, and the error will say "not found", not "wrong region".

The platform

The path of one chat message

All challenges

Browser → chat handler (Lambda Function URL) → Cognito token → orchestrator (AgentCore Runtime) → the Gateway for tools, the specialist for documents, Memory for recall, and Bedrock for reasoning, with a Guardrail wrapped around every model call.

Where the environment sits in AgentCore

AWS overview

The AgentCore Runtime contract

How an agent is hosted

Session ids

The X-Amzn-Bedrock-AgentCore-Runtime-Session-Id header must be at least 33 characters, matching [a-zA-Z0-9][a-zA-Z0-9-_]*. The chat console generates compliant ids; if you test with curl, so must you. Each session is isolated; an idle session times out after 15 minutes by default.

Full-replacement updates

UpdateAgentRuntime and UpdateGateway replace the whole configuration. In the CLI you start from get-agent-runtime, change one field with jq, and send everything back. Sending only the field you changed wipes the rest. The console does this for you, which is why the brief says "console".

The exam's specialist agent is deployed this way from a code package the brief provides; the practice-lab agents are plain Python (standard library plus boto3 vendored into the zip), so there is no Docker build anywhere.

Troubleshooting method

The loop every challenge runs, the evidence that drives it, and the four places a fault can hide.

The loop

Every challenge

Broken system → observable symptom → investigation → evidence → hypothesis → fix → validation → debrief.

The order matters. A fix before evidence is a guess, and a guess in a timed assessment costs the minutes you don't have. The evidence step is almost always one of three things: an error message from the application, a CloudWatch log line, or a resource page in the console that shows a value you didn't expect.

Make it a habit

Before you change anything, write down the one observation you expect to flip (a trace field, a log line, a status). If you can't name it, you haven't found the fault yet.

Four places a fault can hide

The ladder

Every planted fault in the practice labs, and every challenge in the assessment, lives on one of these rungs. Climb from the bottom: the cheapest check first.

LayerExampleHow it shows up

Rung 4 is where the time goes

Challenges C, D and F each require creating a resource with several settings that must match what the application expects (index dimensions and field mappings, namespace strings, regex pattern). Build those in dependency order and copy ids as you go: knowledge base → data source → sync → specialist → orchestrator variable.

Two rules that save more time than any hint

True in every challenge
  • READY is a lifecycle state, not a health check. A runtime is READY with an empty GATEWAY_URL. A knowledge base is Available with zero vectors. A memory is ACTIVE with the wrong namespaces. Validate the behaviour, not the status.
  • Wait for the version, then test. Every runtime edit (env vars, authorizer, network) creates a new version that cycles through UPDATING. Testing early tests the old version and sends you chasing a fault you already fixed.
Check yourself
The trace shows gateway_configured: true, tools_discovered: 0 and warnings: ["gateway: Gateway rejected our token (403)…"]. Which rung?

Rung 2, identity. The URL is set (configuration is fine) but the Gateway's authorizer doesn't trust the token's client id. Fix allowedClients on the Gateway, not the runtime.

You set MEMORY_ID thirty seconds ago and the trace still says memory_configured: false. First move?

Open the runtime and check its status. It is almost certainly UPDATING; the DEFAULT endpoint is still serving the previous version. Wait for READY, then retest.

Shipment questions return SKUs and bay numbers. No warnings, no errors. Which rung?

Rung 3, wiring. The tool was discovered and called, so configuration and identity are fine, and the data came back without error, so execution worked. The target's Lambda ARN routes to the wrong function.

Chapter 04 · Challenge A · Practice lab AM01

Authentication

Challenge A, “The Locked Launchpad”. Restore machine-to-machine OAuth from the chat client to the orchestrator, and learn why a token that Cognito happily issued can still be rejected twice.

What broke

Three planted faults

The chat console says "Authentication service unavailable" to every message, GET /health lists five configuration values as MISSING, and the only app client in the user pool is a browser-style client with no secret. The migration deleted the machine-to-machine client, reset the Lambda's configuration, and left both AgentCore authorizers pointing at the client that survived.

1

No machine-to-machine app client

Cognito user pool · the legacy …-web-client-legacy has no secret and no client_credentials grant

Nothing server-side can obtain an access token. Fix: create a confidential client with the grant and both scopes.

2

AgentCore Gateway + orchestrator Runtime · customJWTAuthorizer.allowedClients

Even a valid token from the new client is rejected with 401/403. Fix: add the new client id to both allowed-clients lists.

3

Chat handler configuration wiped

Lambda environment variables

The handler can't even attempt the token call. Fix: restore the five variables with the existing resources' values.

The client_credentials grant

OAuth 2.0 for software

The OAuth 2.0 flow for software talking to software. There is no user: the client proves its own identity with a client id and a client secret, and receives an access token scoped to resource-server scopes.

Cognito only allows this grant on an app client that has a secret, which is why the console's "Machine-to-machine application" type exists: it generates the secret, enables the grant and asks which custom scopes to allow, in one screen. The resulting token is a JWT. Its payload carries client_id, scope, iss (the pool), exp and token_use: access. It carries no aud claim and no user.

POST https://<COGNITO_DOMAIN>/oauth2/token
Authorization: Basic base64(client_id:client_secret)
Content-Type: application/x-www-form-urlencoded

grant_type=client_credentials&scope=supplychain/read supplychain/write
Analogy

A courier badge issued by head office. It names the courier company, not a person, and it lists the doors it opens. Every door still has its own guard who checks the badge against a list. Head office issuing the badge doesn't put it on anyone's list.

Cache the token

Cognito bills each machine-to-machine token request, and the token is valid for an hour (60 minutes in these labs). The chat handler caches it until a minute before expiry. If you write your own client, do the same.

Resource servers and scopes

supplychain/read · supplychain/write

A resource server is a named API inside the user pool. It defines custom scopes as <identifier>/<scope>: here the identifier is supplychain and the scopes are read and write. A client can only request scopes it has been allowed, and a client-credentials token can only ever contain custom scopes, because there is no user to grant openid or email.

The AgentCore authorizers check the client id. The scopes still matter: the assessment checks that your client is allowed exactly supplychain/read and supplychain/write, and a production gateway can require scopes via "allowed scopes".

Every hop is a separate judge

A bearer token is evidence. Every component that receives it decides for itself whether to trust it, using its own discovery URL (to fetch the issuer's signing keys) and its own allowed clients list. Fixing one judge does not fix the next.

Editing the runtime's authorizer creates a version

Save, then watch the runtime cycle UPDATING → READY before you test. The Gateway update is in place and takes effect immediately.

Token pass-through

How OrbitOps differs from the brief

The orchestrator runtime is configured to forward the inbound Authorization header to the agent code (a request-header allowlist). The code reuses that token for the Gateway and the specialist. It never calls Cognito itself.

The micro-credential's orchestrator does the opposite: it mints its own token, so the brief has you set COGNITO_DOMAIN, COGNITO_CLIENT_ID and COGNITO_USER_POOL_ID on the orchestrator runtime too. The practice-lab orchestrator supports that as a fallback (if no inbound token exists and the Cognito variables are set, it fetches a client-credentials token), but the labs don't need it. The concept being tested is identical: every component that validates or presents the token must know the right client.

Exam angle

Expect to repair the orchestrator's Cognito variables as well as the chat handler's in the assessment. Same values, two places. And because the brief's orchestrator calls Cognito over the internet, its Challenge E keeps a NAT gateway for exactly that reason.

Check yourself
Why does the chat handler mint the token server-side instead of letting the browser call Cognito?

The client secret must never reach a browser. A confidential client lives where its secret can be kept: Lambda environment or a secrets store. The browser only ever talks to the Function URL.

What would change if the authorizers used allowedAudience?

They would look for an aud claim, which a Cognito machine-to-machine access token doesn't carry, so every token would be rejected. allowedClients matches the client_id claim the token does carry.

You created a "traditional web application" client and ticked the client-credentials box. The grant isn't selectable. Why?

That client type has no secret. Cognito only enables client_credentials on a client with a generated secret. The machine-to-machine type sets both up correctly.

Exam angle

M2M = confidential client + client_credentials + resource-server scopes. The assessment checks all three, the exact scope names, and that both authorizers list the new client. Don't replace the pool, the gateway or the runtime; repair them.

Tool routing

Challenge B, “The Case of the Misrouted Cargo Droids”. The orchestrator can chat, but ask about a shipment and it returns stock counts. Learn how an agent discovers tools through a gateway, and why a perfect schema on the wrong ARN gives confident, wrong answers.

What broke

Orchestrator runtime · environment variables

Gateway target · lambdaArn

3

MCP in three messages

Model Context Protocol

The Gateway is an MCP server. A client sends JSON-RPC initialize, then tools/list to discover tools and tools/call to run one. The orchestrator does this at the start of every turn (cached for a minute), if it knows the URL.

POST https://<gateway id>.gateway.bedrock-agentcore.us-west-2.amazonaws.com/mcp
Authorization: Bearer <access token>      Accept: application/json, text/event-stream

{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-03-26",…}}
{"jsonrpc":"2.0","id":2,"method":"tools/list","params":{}}
{"jsonrpc":"2.0","id":3,"method":"tools/call",
 "params":{"name":"logistics-target___track_shipment","arguments":{"shipment_id":"SHP-1001"}}}

Each discovered tool (name, description, inputSchema) becomes a toolSpec in the Bedrock Converse call, so the model sees exactly what the gateway listed and nothing else. When the model picls a tool, the orchestrator sends tools/call and feeds the result back as a toolResult. Up to six rounds per turn.

Analogy

A building directory. The orchestrator employs no specialists of its own; at the start of each turn it reads the directory the gateway publishes, and it can only call what is listed there. No directory address, no services.

What the model sees

Tool names arrive as <target name>___<tool name>, three underscores. With all four targets the gateway lists nine tools; the orchestrator adds a tenth, consult_manuals, once Challenge C is done. tools_discovered counts only the gateway's nine.

Two halves of memory

Short-term and long-term

Short-term memory is the raw conversation: events stored per actorId and sessionId, expiring after the memory's event expiry duration. Long-term memory is what strategies extract from those events, asynchronously, into records grouped by namespace.

Analogy

Short-term memory is the meeting recording: everything, verbatim, deleted eventually. Long-term memory is the file a clerk writes afterwards: a few lines per meeting, filed under the person's name, kept for years. The clerk works on a delay, and files things exactly where the filing rules say.

Namespaces are the contract

The exam's favourite detail

The agent asks for records in a specific namespace. If a strategy writes to a different one, the records exist and the agent never sees them.

A namespace template is a slash-separated path with built-in variables in braces: {actorId}, {sessionId} and {memoryStrategyId}. AgentCore fills them in per event and stores each namespace in a normalised form with one leading and one trailing slash, so the console may show /supplychain/user/{actorId}/preferences/. The content between the slashes is what has to match. Custom variables (tenant, team) are possible but not used here.

Each built-in strategy comes with a default template such as /strategies/{memoryStrategyId}/actors/{actorId}/. Accept the default and extraction works perfectly, writing records exactly where the orchestrator never looks. memory_write: stored, memory_hits: [], forever.

VPC mode changes outbound, not inbound

What actually moves

In VPC mode the runtime attaches elastic network interfaces (ENIs) in your subnets, created through the service-linked role AWSServiceRoleForBedrockAgentCoreNetwork. The agent's outbound calls now originate from private IPs and follow your route tables and security groups. A public subnet is not a shortcut

The runtime's ENI gets a private IP only. Placing it in a public subnet does not give it internet access, and the assessment flags it. Private subnets plus endpoints is the answer; private subnets plus a NAT gateway is the brief's answer for Cognito specifically.

Check yourself
Which endpoints would you still need if the agents used only the knowledge base and no Gateway?

Data plane (bedrock-agentcore, for the A2A call), bedrock-runtime (both models, and Retrieve) and logs. The .gateway endpoint is only for tool traffic.

The chat handler Lambda is not in the VPC. Why does it not need an endpoint to reach the runtime?

Because inbound invocations go to the AWS-managed AgentCore endpoint on the public side, which forwards into your runtime. VPC mode changes where the agent's outbound traffic originates; it doesn't move the front door.

If the orchestrator fetched its own Cognito token, what would you add to the private tier, and what would it cost?

A NAT gateway in a public subnet plus a 0.0.0.0/0 route from the private route table to it (Cognito has no interface endpoint for the token endpoint). Roughly four and a half cents an hour plus an Elastic IP and data processing, per VPC.

Exam angle

Expect checks for four interface endpoints with private DNS, the security group on endpoints and runtimes, VPC mode on both runtimes in the private subnets, runtimes back to READY, and a NAT route for Cognito where the environment's orchestrator mints its own token. A guardrail is evaluated twice

Input gate, output gate

The user's input is checked against every configured policy, in parallel. If it trips one, the model is never called and the blocked input message comes back. If it passes, the model's response is checked the same way; a violation is replaced by the blocked output message, or masked, depending on the policy.

Analogy

Customs at departure and at arrival. The same rulebook is applied to what you carry in (the prompt) and what you carry out (the reply). Some items are confiscated outright (BLOCK); some are allowed through with the serial number taped over (ANONYMIZE).

Where the regex goes

Under sensitive information filters, as a custom pattern with a name (for example supplier-discount-code), the pattern, and an action per side. Not under denied topics, and not under word filters. Lookaround isn't supported; the lab's pattern doesn't need it.

Escaping, three times

Console: DISC-[A-Z]{3}-\d{4}. JSON for the CLI: \\d. Terraform HCL that emits JSON: \\\\d. If the test panel never masks a code, the backslash is usually the reason.

ANONYMIZE keeps the conversation going; BLOCK stops it

Choose per data type

Masking replaces the match with a bracketed placeholder (for PII types, the type name, for example {USERNAME}) and lets the turn continue. Blocking discards the whole turn and returns the configured message. A discount code in a shipment summary is worth masking: the operator still gets the summary. A password is worth blocking: there is no legitimate reply that contains it.

What the PII filter doesn't see

Text only, on the prompt and the response. It does not evaluate tool-call arguments the model generates, tool results your code returns, or tool definitions. DRAFT and versions

Fault 2's other half

A guardrail's working copy is DRAFT. You create numbered versions (1, 2, …) for production. The orchestrator pins GUARDRAIL_VERSION=DRAFT, so your edits take effect on the next model call with no redeploy.

That is ideal for a 40-minute challenge and wrong for production: anyone with edit rights changes the live policy instantly, with no review step. The grown-up pattern is to iterate on DRAFT, create a version, point the application at the version, and roll forward by changing one variable.

Don't touch the version

Changing GUARDRAIL_VERSION to 1 before a version exists produces ResourceNotFoundException on every model call. Leave it at DRAFT; set only GUARDRAIL_ID.

Check yourself
Why anonymize discount codes but block passwords?

A masked code leaves a useful reply (the shipment summary minus the secret). A reply containing a password has no legitimate form, and a prompt that contains one shouldn't be processed at all. ANONYMIZE preserves utility; BLOCK refuses the turn.

Where in the trace would you prove that the output, not the input, triggered the regex?

What it is

Exam lab, not a quiz

A hands-on, timed assessment on AWS Skill Builder. AWS provisions a real account with a broken or incomplete agentic application; you repair and extend it in the console; a Check button grades each challenge against its success criteria.

Exam-day tactics

From people who've sat it
  1. Read the success criteria first, then the tasks. The criteria are what Check grades; the tasks are one way to satisfy them.
  2. Open a scratch note and paste every id you create, in dependency order: client id, KB id, runtime ARN, memory id, guardrail id. Half of each challenge is moving the right string to the right field.
  3. Reuse what's provided. Existing roles, buckets, indexes, pools, gateways. Creating a duplicate wastes minutes and can fail the check that looks at the original.
  4. Keep contract names exactly: logistics-target, quality-target, the namespace strings, the scope names, the environment variable names.
  5. Wait for READY, then Check. Runtime edits create versions. A Check against the old version fails for a reason you already fixed.
  6. Check early. A partial Check tells you which criterion is still unmet. Don't save all six Checks for the last ten minutes.
  7. Synthetic data only for guardrail and memory tests, and the client secret stays out of screenshots and notes you'll keep.
  8. Confirm the region every time you open a new service console.
